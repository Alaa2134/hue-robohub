# BuildX Management — live application integration

The deployed site is static GitHub Pages, not the server-rendered /command route. This revision supersedes the earlier experimental V1 with the actual /app/ integration. Uses existing public.students, public.staff and private.session_student / private.is_staff / private.is_owner. No duplicate logins, no copied student records. Staff access: /app/#/staff/bms; student access: /app/#/me/bms.

Implemented: nested units, explicit multi-role/competition-only appointments, temporary grants and revocation, automatic splitting of explicitly selected students, scoped student/staff supervisors and reviewers, individual/all-group tasks, submissions via text/links, review, applications, expenses, group attendance, leave requests, performance summaries, audit history, and existing in-app notification integration for assignments, appointments, review and competition decisions.

Not yet complete: direct private file upload for BMS, external notifications (WhatsApp/email/push), scheduled weekly reports, certificates, configurable role capability editor, promotion recommendation engine, attendance sync with old sessions, multilingual translation and mobile acceptance tests. Existing staff sectors/tasks and academy remain separate. Never use production student data for test fixtures. The database migration is not deployed by the GitHub Pages workflow; apply only after SQL verification and CI pass.

Backup: original code backup/pre-bms-2026-11-26; earlier prototype backup/bms-v1-2026-11-26. Owner snapshot slot 7 was taken before changes. It is an application-data snapshot, not full PostgreSQL or object-storage backup.

Test: verify owner vs supervisor in unrelated units, watcher cannot mutate, expired/revoked roles, forged student identifiers, anonymous invalid tokens, own task review prohibited, application decisions, archived teams, group splitting, duplicate assignments, task review and attendance. Verify old complaints, registration and public site. Check migration in a disposable database before deploying.

## V3
Private BMS submissions use a dedicated 20 MiB bucket, signed upload/download URLs, server-side ownership checks, up to three attachments and daily ticket limits. Deploy the bms-files edge function only after the migration, and verify anonymous student and authenticated staff requests. Existing email/WhatsApp screens receive owner-selected unit contacts and prefilled messages; no automatic sending, no AI API. Certificates are issued manually by owner through existing QR certificate records after all assigned tasks are completed. Promotion candidates require at least three reviewed tasks in the current month and average 85/100; this never grants permissions. Competition Radar uses public Google News RSS, daily GitHub Actions and a separate public JSON feed; deduplicates and filters by publication date. No paid search or AI API. Chair and Co-chair are assigned on the competition division; review and refer leads to scoped supervisors, who can respond interested/declined. The RSS source is not a guarantee of official registration or complete coverage. No automatic competition registration. GitHub workflow scheduling starts after merge; external sending depends on existing providers, and may have provider quotas. No production migration or edge function deployed as part of this commit. Remaining: integration tests, mobile Arabic localization, automated external delivery if desired, scheduled reports, explicit official-source registry and database/storage restore rehearsal.
